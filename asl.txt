================================================================
ASL — Ave-Shay Language
Query Language Specification v0.2
asdb
================================================================

----------------------------------------------------------------
OVERVIEW
----------------------------------------------------------------
ASL is a pipeline query language for asdb. Queries are composed
of discrete stages. Each stage transforms a stream of documents
and passes it to the next. Execution is left-to-right, lazy,
iterator-based.

A query is a pipeline:
    <source> <stage> <stage> ...

Stages are self-delimiting: a new stage begins wherever a stage
keyword appears in stage position. Separators between stages are
optional decoration (see STAGE SEPARATION below).

----------------------------------------------------------------
SYNTAX CONVENTIONS
----------------------------------------------------------------
- Keywords are lowercase
- Field names are unquoted identifiers
- String literals are double-quoted: "alice"
- Numbers are unquoted: 42, 3.14
- Booleans: true, false
- Null: null
- Comments: -- this is a comment

----------------------------------------------------------------
STAGE SEPARATION
----------------------------------------------------------------
THE RULE:
    A new stage begins wherever a stage keyword appears in stage
    position. Any separator between stages is optional.

Stage keywords are a closed set, which is what makes this
unambiguous:

    from    where   select  drop    order   limit
    offset  group   join    insert  update  delete

Because the keyword itself delimits the stage, all four of these
parse to the identical pipeline:

    from users | where age > 18 | select name      -- pipe
    from users, where age > 18, select name        -- comma
    from users where age > 18 select name          -- nothing

    from users                                     -- newline
    where age > 18
    select name

Pipe and comma are accepted and ignored between stages. Write
whichever reads best. The pipe remains useful as a visual marker
in long one-line queries; the newline form is preferred for
multi-line queries.

WHY NEWLINES NEED NO SPECIAL HANDLING:
The lexer treats a newline as ordinary whitespace and never emits
a token for it. It does not need to. In the multi-line example
above, the `where` keyword on the second line is itself the
delimiter, so the line break is incidental. This means multi-line
queries work with no lexer changes and no significant-whitespace
rules, and a stage may wrap across lines freely:

    from users
    where age > 18
      and country == "CA"        -- continuation, not a new stage
    select name

`and` is not a stage keyword, so the where stage simply continues.

DISAMBIGUATING THE LIST COMMA:
Comma is already load-bearing inside stages: select lists, order
keys, group keys, update assignments, array literals, document
literals, and schema fields all use it. The rule above resolves
this without a special case. At a comma, the token after it
decides:

    select name, email          email is not a keyword
                                -> the select list continues

    select name, where x > 1    where is a stage keyword
                                -> the select stage ended

THE OPTIONAL SEPARATOR IS OPTIONAL ONLY IN STAGE POSITION:
This is the limit of the rule above and it is load-bearing. A
separator may be omitted only where a stage keyword follows.
Inside a list the comma is MANDATORY.

    select name, email          two projections
    select name email           NOT two projections, this is an
                                error

The reason is that juxtaposition already means something else in
select position: it is how an aggregate takes its argument.

    select sum total            one item, sum(total)
    select sum, total           two items, the aggregate `sum`
                                and the field `total`

If bare juxtaposition also meant "next list item", those two
would be indistinguishable. Keeping the omitted separator legal
only in stage position is what buys that back, because a stage
keyword can never be an aggregate argument.

The same holds for order keys, group keys, update assignments,
and array/document literals: all take mandatory commas. So the
four "equivalent forms" claim above is precisely about the
boundary BETWEEN stages, not about anything inside one.

RESERVED WORDS (already paid for in v0.1):
Stage keywords are reserved and cannot be used as bare field
names. Without this, `select level, order` would be ambiguous:
`order` could be a third projection or the start of an order
stage.

This looks like the cost of separator-optional syntax, and it is
worth being precise that it is NOT. The v0.1 lexer already maps
every one of these words to its own token unconditionally, so
`select level, order` is already a parse error today. v0.2
reserves nothing new. It spends a restriction the language had
already taken on and was not using for anything.

What v0.2 adds is the way OUT of that restriction, which v0.1
does not have at all. A field whose name collides with a stage
keyword can be backtick-quoted:

    from logs select level, `order`

Before this there was simply no way to name such a field. So on
the reserved-word axis v0.2 is strictly a gain, not a trade.

This is the same shape SQL uses: keywords delimit clauses,
commas delimit lists, and quoting escapes a collision.

RELATIONSHIP TO OTHER LANGUAGES:
This is deliberately not MongoDB's model. Mongo queries are DATA
(JSON documents describing a query), which serializes trivially
but composes awkwardly and needs a separate API per operation
shape (find vs aggregate vs updateOne). ASL queries are LANGUAGE
(text parsed into one uniform pipeline). SQL is closer, in that
its clauses are also self-delimiting keywords with no separators,
but SQL writes SELECT first while executing FROM first. ASL keeps
reading order and execution order identical.

----------------------------------------------------------------
DATA MODEL
----------------------------------------------------------------
shaydb stores collections of documents.
A document is a set of key-value pairs.
Values can be:
    - Int        64-bit signed integer
    - Float      64-bit float
    - String     UTF-8 text
    - Bool       true | false
    - Null       null
    - Array      [val, val, ...]
    - Document   { key: val, key: val, ... }  (nested)

----------------------------------------------------------------
SOURCE STAGES
----------------------------------------------------------------
Every pipeline must begin with exactly one source stage.

    from <collection>
        Scans all documents in a collection.
        Example:
            from users

    from <collection> use index <field>
        Hints the executor to use an index on <field>.
        Example:
            from users use index age

----------------------------------------------------------------
FILTER STAGE
----------------------------------------------------------------
    where <expr>
        Retains documents where <expr> evaluates to true.
        Discards all others.

    Comparison operators:
        ==   equal
        !=   not equal
        >    greater than
        >=   greater than or equal
        <    less than
        <=   less than or equal

    Logical operators:
        and, or, not

    Membership:
        <field> in [val, val, ...]
        <field> not in [val, val, ...]

    Existence:
        exists <field>       document has this field
        missing <field>      document does not have this field

    String matching:
        <field> contains "substr"
        <field> starts "prefix"
        <field> ends "suffix"

    Examples:
        from users | where age > 18
        from users | where age > 18 and country == "CA"
        from users | where name contains "ali"
        from orders | where status in ["pending", "shipped"]
        from logs | where exists error_code

----------------------------------------------------------------
PROJECTION STAGE
----------------------------------------------------------------
    select <field>, <field>, ...
        Emits only the specified fields from each document.
        Example:
            from users | select name, email

    select *
        Emits all fields. Default if select is omitted.

    select <field> as <alias>, ...
        Renames a field in the output.
        Example:
            from users | select name, age as years

    drop <field>, <field>, ...
        Emits all fields except those listed.
        Example:
            from users | drop password, internal_id

----------------------------------------------------------------
SORTING STAGE
----------------------------------------------------------------
    order <field> asc
    order <field> desc
    order <field> asc, <field> desc   (multi-key)

    Examples:
        from users | order age desc
        from users | order country asc, age desc

----------------------------------------------------------------
PAGINATION STAGES
----------------------------------------------------------------
    limit <n>
        Emits at most n documents.
        Example:
            from users | limit 10

    offset <n>
        Skips the first n documents.
        Example:
            from users | offset 20 | limit 10

    Canonical pagination pattern:
        from users | order id asc | offset 100 | limit 25

----------------------------------------------------------------
AGGREGATION STAGES
----------------------------------------------------------------
    group <field>
        Groups documents by the value of <field>.
        Must be followed by an aggregate select.

    group <field>, <field>, ...
        Groups by composite key.

    Aggregate functions (used inside select after group):
        count           number of documents in group
        sum <field>     sum of field values
        avg <field>     average of field values
        min <field>     minimum field value
        max <field>     maximum field value
        collect <field> array of all values in group

    Examples:
        from orders | group status | select status, count
        from orders | group user_id | select user_id, sum total
        from users  | group country | select country, count, avg age

----------------------------------------------------------------
MUTATION STAGES
----------------------------------------------------------------
Mutation pipelines source from a collection and terminate in
a mutation stage. They do not return document streams — they
return a result summary { affected: n }.

    insert { key: val, key: val, ... }
        Inserts a single document into the source collection.
        Example:
            from users | insert { name: "alice", age: 25 }

    insert [ { ... }, { ... }, ... ]
        Batch insert.
        Example:
            from users | insert [{ name: "bob" }, { name: "carol" }]

    update set <field> = <val>, ...
        Updates matching documents. Combine with where.
        Example:
            from users | where id == 1 | update set age = 26

    update set <field> = <field> + <val>
        Field expression update.
        Example:
            from orders | where status == "pending" | update set retries = retries + 1

    delete
        Deletes all documents passing through the pipeline.
        Example:
            from users | where age < 0 | delete

----------------------------------------------------------------
JOIN STAGE
----------------------------------------------------------------
    join <collection> on <left_field> == <right_field>
        Hash join. Matches documents from the left stream
        with documents from the right collection.
        Example:
            from orders | join users on user_id == id | select name, total

    join type defaults to inner. Outer joins are out of scope for v1.

----------------------------------------------------------------
FIELD EXPRESSIONS
----------------------------------------------------------------
Field expressions can appear in where, select, update set,
and order stages.

    Arithmetic:     +  -  *  /  %
    String concat:  field + " suffix"
    Ternary:        if <expr> then <val> else <val>

    Examples:
        from products | select name, price * 1.13 as price_with_tax
        from users | select name, if age >= 18 then "adult" else "minor" as group

----------------------------------------------------------------
SCHEMA DEFINITION
----------------------------------------------------------------
Collections are created with a schema declaration.
Schema is optional — schemaless documents are permitted —
but declared fields are indexable and type-checked on insert.

    create <collection> { <field>: <type>, ... }

    Types:
        int, float, string, bool, any

    Constraints (optional, inline):
        required    field must be present on insert
        unique      enforce uniqueness via index

    Examples:
        create users { id: int required unique, name: string required, age: int }
        create logs  { timestamp: int required, message: string, level: string }

    Drop a collection:
        drop collection <name>

----------------------------------------------------------------
INDEX DEFINITION
----------------------------------------------------------------
    create index on <collection>.<field>
    create index on <collection>.<field>, <field>   (composite)
    drop index on <collection>.<field>

    Examples:
        create index on users.id
        create index on orders.user_id, orders.status

----------------------------------------------------------------
RESULT FORMAT
----------------------------------------------------------------
Query pipelines return a document stream serialized as:

    {
      "count": <n>,
      "documents": [ { ... }, { ... }, ... ]
    }

Mutation pipelines return:

    {
      "affected": <n>
    }

Error responses:

    {
      "error": "<message>",
      "stage": "<stage where error occurred>"
    }

----------------------------------------------------------------
EXAMPLES — FULL QUERIES
----------------------------------------------------------------

-- All adult users in Canada, sorted by name
from users | where age >= 18 and country == "CA" | order name asc | select name, email

-- Paginate products by price descending
from products | order price desc | offset 0 | limit 25 | select name, price

-- Order summary per user
from orders | group user_id | select user_id, count, sum total | order sum desc

-- Join orders with users
from orders | where status == "shipped" | join users on user_id == id | select name, total, shipped_at

-- Insert a document
from users | insert { name: "alice", age: 25, country: "CA" }

-- Update a field
from users | where id == 42 | update set age = 26

-- Delete stale sessions
from sessions | where expires < 1700000000 | delete

-- Schemaless insert (no schema required)
from events | insert { type: "click", element: "btn-signup", ts: 1700000000 }

-- The same query in all four separator styles (v0.2)
from users | where age >= 18 | select name, email
from users, where age >= 18, select name, email
from users where age >= 18 select name, email

from users
where age >= 18
select name, email

-- Multi-line with a stage wrapping across lines
from orders
where status == "shipped"
  and total > 100
join users on user_id == id
select name, total
order total desc
limit 25

----------------------------------------------------------------
OUT OF SCOPE — v1
----------------------------------------------------------------
- Transactions / multi-statement atomicity
- Subqueries
- Outer joins
- Window functions
- Full-text search
- User permissions / auth
- Replication

----------------------------------------------------------------
CHANGELOG
----------------------------------------------------------------
v0.2
  - Stage separation reworked: stages are now self-delimiting by
    keyword. Pipe, comma, newline, and nothing at all are all
    accepted and equivalent between stages. See STAGE SEPARATION.
  - Stage keywords are now reserved words. Backtick-quoting added
    for field names that collide with them.
  - Rationale for diverging from MongoDB's query-as-data model
    recorded in STAGE SEPARATION.

v0.1
  - Initial specification. Pipe-only stage separation.

================================================================
asdb v1.0.0 — Implementation Plan / Current Status
================================================================

Last verified: Phase 4 complete. `cargo test` passes with
110 passed, 3 ignored.

This file is both a plan and a reflection of current functionality. Completed
phases describe what the code does now. Future phases describe the remaining
work, scoped to the current architecture.

----------------------------------------------------------------
PRINCIPLES
----------------------------------------------------------------
- Build bottom-up: nothing above depends on something unbuilt below
- Every phase ends with something runnable and testable
- Benchmark at the end of major storage/index phases
- Keep it compiling at all times
- Each milestone is a commit-worthy state
- Keep the core engine hand-rolled unless a crate is clearly only interface
  polish (CLI parsing, line editing, output formatting)

----------------------------------------------------------------
PHASE 1 — STORAGE ENGINE
Status: COMPLETE
----------------------------------------------------------------
Goal: read and write raw records to disk reliably.

  1.1  Page abstraction
       Status: complete
       - PAGE_SIZE = 4096
       - Page struct backed by [u8; 4096]
       - PageId = u64
       - Tests verify raw page bytes round-trip correctly

  1.2  DiskManager
       Status: complete
       - Opens/creates a single database file
       - read_page(page_id) -> Page
       - write_page(page_id, page)
       - allocate_page() -> PageId
       - free_page(page_id), with free-list reuse and double-free rejection
       - Rejects malformed partial-page files
       - Ignored stress test covers 10k page allocate/write/read

  1.3  BufferPool
       Status: complete
       - Fixed-size frame pool
       - Page table: PageId -> frame
       - LRU-style eviction
       - Dirty tracking and flush-on-evict
       - Pin/unpin behavior
       - Page deletion
       - Tests cover fetch, eviction round-trip, and delete

  1.4  Heap file
       Status: complete
       - Slotted-page variable-length record storage
       - DocId = (PageId, SlotId)
       - insert(bytes) -> DocId
       - read(DocId) -> Option<Vec<u8>>
       - delete(DocId), tombstoning slot
       - scan_all() -> Vec<(DocId, Vec<u8>)>
       - Multi-page chains and persistence across reopen
       - Ignored stress test covers 100k variable records

  Phase 1 milestone:
    Complete. Raw blobs can be inserted, read by DocId, flushed,
    reopened, and read back unchanged.

----------------------------------------------------------------
PHASE 2 — DOCUMENT + COLLECTION LAYER
Status: COMPLETE
----------------------------------------------------------------
Goal: structured documents on top of raw heap storage.

  2.1  Document model and codec
       Status: complete
       - Value enum:
           Int | Float | String | Bool | Null |
           Array(Vec<Value>) | Document(HashMap<String, Value>)
       - BSON-inspired binary codec
       - serialize_document(&Document) -> Vec<u8>
       - deserialize_document(&[u8]) -> Result<Document, DecodeError>
       - Tests cover nested docs, invalid tags, trailing bytes
       - Ignored stress test covers 10k generated document round-trips

  2.2  Collection
       Status: complete
       - Thin document API over HeapFile
       - insert(&Document) -> DocId
       - get(DocId) -> Result<Option<Document>>
       - delete(DocId)
       - scan() -> Vec<(DocId, Document)>
       - flush()
       - Persist/reopen by known heap root

  2.3  Catalog
       Status: complete
       - Catalog is persisted on page 0
       - Page 0 is reserved before collection/index pages are allocated
       - Tracks collection name -> heap root page
       - Tracks index metadata: collection + field -> BTree root page
       - create_collection(name)
       - drop_collection(name)
       - open_collection(name) -> Collection
       - create/drop index metadata support for Phase 3
       - Persists across restart
       - Tests cover page-0 reservation, reopen, drop, malformed catalog data,
         and Phase 2 milestone reopen/scan count

  Current limitation:
    Collection owns its HeapFile/BufferPool. Higher-level coordination is still
    manual until a Database owner is introduced in a future phase.

  Phase 2 milestone:
    Complete. A database can reserve catalog page 0, create a collection,
    insert documents, flush/restart, reopen by name, and scan the same count.

----------------------------------------------------------------
PHASE 3 — B-TREE INDEX
Status: COMPLETE
----------------------------------------------------------------
Goal: fast point lookups and range scans on indexed fields.

  3.1  BTreeNode
       Status: complete
       - Internal nodes store keys + child PageIds
       - Leaf nodes store keys + DocIds + next-leaf pointer
       - Nodes serialize to/from one 4KB Page
       - Max key count is computed from page layout

  3.2  BTree operations
       Status: complete
       - BTree::new(pool)
       - BTree::open(pool, root)
       - root()
       - search(key) -> Option<DocId>
       - insert(key, DocId)
       - delete(key)
       - range_scan(low, high) -> Vec<DocId>
       - free()
       - Handles root and leaf splits
       - Handles delete underflow through redistribution/merge
       - Supports duplicate keys ordered by DocId
       - Tests cover empty search, inserts, splits, range scan, duplicate keys,
         leaf deletes, merge/redistribute, and deeper delete sequences

  3.3  Index integration
       Status: complete
       - IndexManager maps collection + field to BTree root PageId through
         catalog index metadata
       - create(collection, field) backfills existing documents
       - drop(collection, field) removes metadata and frees tree pages
       - on_insert(collection, doc, doc_id)
       - on_delete(collection, doc, doc_id)
       - search(collection, field, value)
       - range_scan(collection, field, low, high)
       - Tests cover missing collection, backfill, insert maintenance, delete
         maintenance, drop, and catalog persistence

  3.4  Key encoding
       Status: complete
       - serialize_key(&Value) -> Vec<u8>
       - Sort-preserving encodings for Int and Float
       - Stable type tags for Null, Bool, Int, Float, String
       - NaN is rejected
       - Array and Document are intentionally unsupported as index keys

  3.5  Benchmarks
       Status: complete
       - Bench binary: src/bin/bench.rs
       - Env-configurable run sizes
       - Sequential vs random insert
       - Point lookup p50/p95/p99
       - Range scans at 0.1%, 1%, 10%
       - Indexed lookup vs real Collection::scan crossover
       - Buffer pool pressure at 10%, 50%, 100% estimated working set

       Teach.cs run:
       - Sequential insert, 10M keys:
           5.63s, 1,774,786 ops/sec
       - Random insert, 10M keys:
           58.88s, 169,838 ops/sec
       - Point lookup, 1M random lookups:
           p50 5.01us, p95 5.44us, p99 6.31us
       - Range scan:
           0.1%: 1,000 docs in 0.09ms
           1.0%: 10,000 docs in 0.72ms
           10.0%: 100,000 docs in 6.71ms
       - Indexed lookup beat decoded collection scan at all measured sizes
         from 100 through 100,000 documents
       - Buffer pool pressure over ~80,001 page working set:
           10% pool: 105,231 lookups/sec
           50% pool: 2,307,852 lookups/sec
           100% pool: 2,349,886 lookups/sec

  Current caller contract:
    Index updates are caller-coordinated for now.

      let doc_id = collection.insert(&doc)?;
      index_manager.on_insert("users", &doc, doc_id)?;

      let doc = collection.get(doc_id)?.unwrap();
      collection.delete(doc_id)?;
      index_manager.on_delete("users", &doc, doc_id)?;

    This is acceptable until the Database owner phase centralizes collection
    and index ownership.

  Phase 3 milestone:
    Complete. BTree and IndexManager support indexed point/range access, index
    backfill, insert/delete maintenance, and teach-scale benchmarks.

PHASE 4 — ASL LEXER + PARSER
Status: COMPLETE
----------------------------------------------------------------
Goal: tokenize and parse ASL into an AST. No execution happens here.

  4.1  Token definitions
       Status: complete
       - Keywords:
           from, where, select, order, limit, offset, group, join,
           insert, update, delete, drop, create, index, on, set, as,
           in, exists, missing, contains, starts, ends, use, asc, desc,
           and, or, not, if, then, else, true, false, null, required,
           unique, any
       - Literals: IntLit, FloatLit, StringLit
       - Identifiers
       - Operators: == != > >= < <= + - * / % | =
       - Punctuation: { } [ ] ( ) , : .

  4.2  Lexer
       Status: complete
       - Input: &str
       - Output: Vec<Spanned<Token>>
       - Hand-rolled, no external crates
       - Handles whitespace and -- line comments
       - Handles string escapes and Unicode inside strings
       - Tracks line/column for errors
       - Tests cover exact milestone token stream and representative queries

  4.3  AST definitions
       Status: complete
       - Statement:
           Pipeline(Pipeline)
           CreateCollection { name, schema }
           DropCollection { name }
           CreateIndex { collection, fields }
           DropIndex { collection, fields }
       - Pipeline = Vec<Stage>
       - Stage:
           From { collection, index_hint }
           Where { expr }
           Select { items }
           Drop { fields }
           Order { keys }
           Limit { n }
           Offset { n }
           Group { fields }
           Join { collection, left_field, right_field }
           Insert { docs }
           Update { assignments }
           Delete
       - Expr:
           Field, Lit, BinOp, UnaryOp, In, Exists, Missing,
           StringMatch, Ternary, ArrayLit, DocLit, AggCall
       - Schema AST supports int, float, string, bool, any plus required/unique
       - Document literals preserve field order for deterministic inserts

  4.4  Parser
       Status: complete
       - Input: &[Spanned<Token>]
       - Output: Statement
       - Recursive descent parser
       - Parses top-level DDL statements and pipelines
       - Parses expression precedence for or/and/not/comparison/arithmetic
       - Parses if/then/else ternaries
       - Parses select aliases and simple aggregate forms
       - Parses insert document/batch literals and nested arrays/documents
       - Parses update assignments and delete stages
       - Reports parse errors with line/column
       - Tests cover milestone AST, representative queries, precedence,
         malformed constructs, schema parsing, index DDL, and mutation syntax

  Phase 4 milestone:
    Complete. This query parses without error and matches the expected AST:

      from users | where age > 18 and country == "CA"
                 | order name asc
                 | select name, email
                 | limit 25

  Important boundary:
    Phase 4 parses DDL and mutation syntax, but does not execute it. Creating
    collections, creating indexes, inserting, querying, updating, and deleting
    real data are Phase 5+ runtime work.

PHASE 5 — QUERY ENGINE V1
Status: IN PROGRESS
----------------------------------------------------------------
Goal: execute the useful Phase 4 AST surface against real data.

Scope rule:
  Phase 5 should deliver the end-to-end demo and common single-collection
  queries first. Joins, grouping, aggregate execution, and external sort are
  parsed already, but can move to Phase 6/7 if they threaten the v1 milestone.

Current query module state:
  src/query/binder.rs, planner.rs, and executor.rs exist as empty modules.

  5.1  Runtime owner
       Status: complete
       - Introduce Database as the public execution owner
       - Database opens one database file
       - Database owns or coordinates:
           Catalog
           collection access
           IndexManager
           shared BufferPool/DiskManager strategy
       - Hide the current caller-coordinated index maintenance behind Database
         insert/delete APIs
       - Avoid separate Collection and IndexManager views of the same file
         causing flush-boundary surprises

       Implemented:
       - Database::create(path)
       - Database::open(path)
       - has_collection(name)
       - has_index(collection, field)
       - create_collection(name)
       - drop_collection(name), including dropping that collection's indexes
       - create_index(collection, field)
       - drop_index(collection, field)
       - insert_doc(collection, doc), including index maintenance
       - delete_doc(collection, doc_id), including pre-delete document fetch
         and index maintenance
       - get_doc(collection, doc_id)
       - scan_collection(collection)
       - search_index(collection, field, value)
       - range_index(collection, field, low, high)

       Tests cover:
       - create/reopen collection
       - insert and scan
       - index backfill
       - insert updates index
       - delete updates index
       - indexed range fetches documents
       - reopen preserves data and index metadata
       - drop collection removes indexes

  5.2  Binder / validation
       - Accept Statement from parser
       - Reject nonexistent collections
       - Reject nonexistent indexes for explicit `use index`
       - Validate DDL shape:
           create collection name not already used
           create index target collection exists
           schema field names are unique
       - Validate pipeline order enough for v1:
           pipeline starts with From
           Insert/Update/Delete are terminal
           stages that need a source have one
       - Schema-aware field/type checking can be basic at first because
         catalog schema persistence is not complete yet

  5.3  Expression evaluator
       - eval(expr, document) -> Value
       - truthiness / boolean checks for where
       - Comparisons: == != > >= < <=
       - Boolean ops: and, or, not
       - Arithmetic: + - * / %
       - Unary negation
       - In / not in
       - Exists / missing
       - String contains / starts / ends
       - Ternary if/then/else
       - Int/float coercion where sensible
       - Clear errors for invalid type combinations

  5.4  Planner V1
       - Bound pipeline -> physical plan
       - Physical operators for v1:
           SeqScan
           IndexScan for simple indexed predicates
           Filter
           Projection / Drop
           Limit / Offset
           Insert
           Delete
           CreateCollection
           CreateIndex
           DropCollection
           DropIndex
       - Simple index rule:
           use IndexScan for single-field indexed predicates:
             field == literal
             field > literal
             field >= literal
             field < literal
             field <= literal
             bounded `and` range on the same field
           otherwise use SeqScan + Filter
       - No cost model in v1

  5.5  Executor V1
       - Execute physical plan against Database
       - For read pipelines, return Vec<Document> initially
       - Keep operator boundaries clean enough to move toward streaming later
       - SeqScan reads Collection::scan()
       - IndexScan gets DocIds from IndexManager then fetches docs by DocId
       - Filter applies expression evaluator
       - Projection builds output documents
       - Limit/Offset apply result slicing

  5.6  Mutation execution
       - Insert:
           convert parsed DocLiteral to Document
           call Database::insert_doc
       - Delete:
           identify matching DocIds
           call Database::delete_doc
       - Update:
           either defer to a later phase, or implement as delete+insert/rewrite
           with correct index maintenance. Do not fake this if HeapFile has no
           update-in-place API.

  5.7  Persistence
       - DDL and mutations flush as needed for restart tests
       - Restart process, reopen Database, rerun query, same result

  Phase 5 milestone:
    End to end:

      create users { id: int required unique, name: string, age: int }
      create index on users.id
      from users | insert { id: 1, name: "alice", age: 25 }
      from users | insert { id: 2, name: "bob", age: 17 }
      from users | where age >= 18 | select name, age
        -> [{ name: "alice", age: 25 }]

    Restart. Query again. Same result.

  Phase 5 test target:
    - DDL creates persistent collections and indexes
    - Insert updates indexes
    - Where/select/limit/offset over SeqScan
    - Where/select over IndexScan
    - Delete updates indexes
    - Restart preserves catalog, data, and index metadata

PHASE 6 — QUERY FEATURES + INTERFACE
Status: FUTURE
----------------------------------------------------------------
Goal: turn the Phase 5 engine into something pleasant to use and broaden the
query surface beyond the v1 milestone.

  6.1  Streaming executor cleanup
       - Replace read pipeline materialization with iterator-like operators
       - Preserve Vec<Document> convenience at the public API boundary
       - Avoid materializing full scans except for operators that need it

  6.2  Sort / order by
       - In-memory sort for modest result sets
       - External sort can remain future work unless needed by benchmarks
       - Respect asc/desc over comparable Value types

  6.3  Update execution
       - Add HeapFile/Collection rewrite support, or implement safe
         delete+insert semantics
       - Maintain indexes for changed indexed fields
       - Return updated row count

  6.4  Group and aggregate execution
       - HashAggregate for parsed `group`
       - count, sum initially
       - Later: avg, min, max

  6.5  Join execution
       - Start with hash join for equality joins
       - Use parsed Join stage:
           join <collection> on left_field == right_field
       - Add tests with small collections first

  6.6  REPL
       - Read a line, execute ASL, print result
       - Multi-line input when a trailing | suggests continuation
       - .help, .collections, .schema <name>, .quit
       - Pretty-print document results as a table

  6.7  File execution
       - asdb run query.asl
       - Read ASL from file, execute, print results

  6.8  CLI
       - asdb repl
       - asdb run <file>
       - asdb bench
       - asdb info

  6.9  Error messages
       - Every public error says what went wrong and where
       - No panics in normal operation
       - Convert parser/binder/planner/executor/storage errors into friendly
         top-level diagnostics

  6.10 README
       - What asdb is
       - ASL by example
       - Architecture overview
       - Current phase status
       - Benchmark results from teach.cs

PHASE 7 — BENCHMARKS + ENGINE POLISH
Status: FUTURE
----------------------------------------------------------------
Goal: measure and improve the full database, not just the BTree.

  B1  Insert throughput
      - Sequential insert: 1M, 5M, 10M documents
      - Random indexed field values: same sizes
      - Measure docs/sec and wall time with and without indexes

  B2  Point lookup latency
      - Indexed vs non-indexed lookup
      - 1M random lookups on large collection
      - Measure p50, p95, p99 latency

  B3  Range scan selectivity
      - 0.1%, 1%, 10%, 50% of collection
      - Indexed range vs sequential scan
      - Find real crossover point for decoded documents

  B4  Buffer pool pressure
      - 10%, 25%, 50%, 100% of working set
      - Measure throughput degradation
      - Record eviction and dirty flush stats if instrumentation exists

  B5  Write amplification
      - Measure physical bytes written vs logical bytes inserted
      - Compare unindexed and indexed collections

  B6  Optimizer polish
      - Add basic index selectivity estimates if needed
      - Keep simple rule-based planner until measurements justify more

----------------------------------------------------------------
OUT OF SCOPE — v1
----------------------------------------------------------------
- WAL / crash recovery / transactions
- Concurrent access / locking
- Outer joins
- Subqueries / nested pipelines
- Full cost-based optimizer
- Replication / distribution
- Auth / permissions
- Network protocol / server mode

These are v2 starting points, not failures of v1.

----------------------------------------------------------------
STRETCH GOALS
----------------------------------------------------------------
- WAL: append-only log, replay on crash recovery
- Server mode: TCP socket, send ASL queries over the wire
- NUMA-aware buffer pool
- External sort for very large ordered results
- More aggregate functions
- Schema persistence beyond the current AST/catalog roots

----------------------------------------------------------------
SUGGESTED CRATES
----------------------------------------------------------------
- none required for core engine
- serde_json: optional result output formatting
- clap: optional CLI argument parsing
- rustyline: optional REPL line editing

Everything else — storage, BTree, parser, binder, planner, executor — should
remain hand-rolled unless there is a deliberate reason to change that.

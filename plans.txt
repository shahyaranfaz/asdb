================================================================
asdb v1.0.0 — Implementation Plan / Current Status
================================================================

Last verified: 2026-08-06. Phases 1-5 and the implemented portions of
Phase 6 pass `cargo test` with 207 passed, 4 ignored, 0 failed.

This file is both a plan and a reflection of current functionality. Completed
phases describe what the code does now. Future phases describe the remaining
work, scoped to the current architecture.

----------------------------------------------------------------
PRINCIPLES
----------------------------------------------------------------
- Build bottom-up: nothing above depends on something unbuilt below
- Every phase ends with something runnable and testable
- Benchmark at the end of major storage/index phases
- Keep it compiling at all times
- Each milestone is a commit-worthy state
- Keep the core engine hand-rolled unless a crate is clearly only interface
  polish (CLI parsing, line editing, output formatting)

----------------------------------------------------------------
PHASE 1 — STORAGE ENGINE
Status: COMPLETE
----------------------------------------------------------------
Goal: read and write raw records to disk reliably.

  1.1  Page abstraction
       Status: complete
       - PAGE_SIZE = 4096
       - Page struct backed by [u8; 4096]
       - PageId = u64
       - Tests verify raw page bytes round-trip correctly

  1.2  DiskManager
       Status: complete
       - Opens/creates a single database file
       - read_page(page_id) -> Page
       - write_page(page_id, page)
       - allocate_page() -> PageId
       - free_page(page_id), with free-list reuse and double-free rejection
       - Rejects malformed partial-page files
       - Ignored stress test covers 10k page allocate/write/read

  1.3  BufferPool
       Status: complete
       - Fixed-size frame pool
       - Page table: PageId -> frame
       - LRU-style eviction
       - Dirty tracking and flush-on-evict
       - Pin/unpin behavior
       - Page deletion
       - Tests cover fetch, eviction round-trip, and delete

  1.4  Heap file
       Status: complete
       - Slotted-page variable-length record storage
       - DocId = (PageId, SlotId)
       - insert(bytes) -> DocId
       - read(DocId) -> Option<Vec<u8>>
       - delete(DocId), tombstoning slot
       - scan_all() -> Vec<(DocId, Vec<u8>)>
       - Multi-page chains and persistence across reopen
       - Ignored stress test covers 100k variable records

  Phase 1 milestone:
    Complete. Raw blobs can be inserted, read by DocId, flushed,
    reopened, and read back unchanged.

PHASE 2 — DOCUMENT + COLLECTION LAYER
Status: COMPLETE
----------------------------------------------------------------
Goal: structured documents on top of raw heap storage.

  2.1  Document model and codec
       Status: complete
       - Value enum:
           Int | Float | String | Bool | Null |
           Array(Vec<Value>) | Document(HashMap<String, Value>)
       - BSON-inspired binary codec
       - serialize_document(&Document) -> Vec<u8>
       - deserialize_document(&[u8]) -> Result<Document, DecodeError>
       - Tests cover nested docs, invalid tags, trailing bytes
       - Ignored stress test covers 10k generated document round-trips

  2.2  Collection
       Status: complete
       - Thin document API over HeapFile
       - insert(&Document) -> DocId
       - get(DocId) -> Result<Option<Document>>
       - delete(DocId)
       - scan() -> Vec<(DocId, Document)>
       - flush()
       - Persist/reopen by known heap root

  2.3  Catalog
       Status: complete
       - Catalog is persisted on page 0
       - Page 0 is reserved before collection/index pages are allocated
       - Tracks collection name -> heap root page
       - Tracks index metadata: collection + field -> BTree root page
       - create_collection(name)
       - drop_collection(name)
       - open_collection(name) -> Collection
       - create/drop index metadata support for Phase 3
       - Persists across restart
       - Tests cover page-0 reservation, reopen, drop, malformed catalog data,
         and Phase 2 milestone reopen/scan count

  Current limitation:
    Collection owns its HeapFile/BufferPool. Higher-level coordination is still
    manual until a Database owner is introduced in a future phase.

  Phase 2 milestone:
    Complete. A database can reserve catalog page 0, create a collection,
    insert documents, flush/restart, reopen by name, and scan the same count.

PHASE 3 — B-TREE INDEX
Status: COMPLETE
----------------------------------------------------------------
Goal: fast point lookups and range scans on indexed fields.

  3.1  BTreeNode
       Status: complete
       - Internal nodes store keys + child PageIds
       - Leaf nodes store keys + DocIds + next-leaf pointer
       - Nodes serialize to/from one 4KB Page
       - Max key count is computed from page layout

  3.2  BTree operations
       Status: complete
       - BTree::new(pool)
       - BTree::open(pool, root)
       - root()
       - search(key) -> Option<DocId>
       - insert(key, DocId)
       - delete(key)
       - range_scan(low, high) -> Vec<DocId>
       - free()
       - Handles root and leaf splits
       - Handles delete underflow through redistribution/merge
       - Supports duplicate keys ordered by DocId
       - Tests cover empty search, inserts, splits, range scan, duplicate keys,
         leaf deletes, merge/redistribute, and deeper delete sequences

  3.3  Index integration
       Status: complete
       - IndexManager maps collection + field to BTree root PageId through
         catalog index metadata
       - create(collection, field) backfills existing documents
       - drop(collection, field) removes metadata and frees tree pages
       - on_insert(collection, doc, doc_id)
       - on_delete(collection, doc, doc_id)
       - search(collection, field, value)
       - range_scan(collection, field, low, high)
       - Tests cover missing collection, backfill, insert maintenance, delete
         maintenance, drop, and catalog persistence

  3.4  Key encoding
       Status: complete
       - serialize_key(&Value) -> Vec<u8>
       - Sort-preserving encodings for Int and Float
       - Stable type tags for Null, Bool, Int, Float, String
       - NaN is rejected
       - Array and Document are intentionally unsupported as index keys

  3.5  Benchmarks
       Status: complete
       - Bench binary: src/bin/bench.rs
       - Env-configurable run sizes
       - Sequential vs random insert
       - Point lookup p50/p95/p99
       - Range scans at 0.1%, 1%, 10%
       - Indexed lookup vs real Collection::scan crossover
       - Buffer pool pressure at 10%, 50%, 100% estimated working set

       Teach.cs run:
       - Sequential insert, 10M keys:
           5.63s, 1,774,786 ops/sec
       - Random insert, 10M keys:
           58.88s, 169,838 ops/sec
       - Point lookup, 1M random lookups:
           p50 5.01us, p95 5.44us, p99 6.31us
       - Range scan:
           0.1%: 1,000 docs in 0.09ms
           1.0%: 10,000 docs in 0.72ms
           10.0%: 100,000 docs in 6.71ms
       - Indexed lookup beat decoded collection scan at all measured sizes
         from 100 through 100,000 documents
       - Buffer pool pressure over ~80,001 page working set:
           10% pool: 105,231 lookups/sec
           50% pool: 2,307,852 lookups/sec
           100% pool: 2,349,886 lookups/sec

  Current caller contract:
    Index updates are caller-coordinated for now.

      let doc_id = collection.insert(&doc)?;
      index_manager.on_insert("users", &doc, doc_id)?;

      let doc = collection.get(doc_id)?.unwrap();
      collection.delete(doc_id)?;
      index_manager.on_delete("users", &doc, doc_id)?;

    This is acceptable until the Database owner phase centralizes collection
    and index ownership.

  Phase 3 milestone:
    Complete. BTree and IndexManager support indexed point/range access, index
    backfill, insert/delete maintenance, and teach-scale benchmarks.

PHASE 4 — ASL LEXER + PARSER
Status: COMPLETE
----------------------------------------------------------------
Goal: tokenize and parse ASL into an AST. No execution happens here.

  4.1  Token definitions
       Status: complete
       - Keywords:
           from, where, select, order, limit, offset, group, join,
           insert, update, delete, drop, create, index, on, set, as,
           in, exists, missing, contains, starts, ends, use, asc, desc,
           and, or, not, if, then, else, true, false, null, required,
           unique, any
       - Literals: IntLit, FloatLit, StringLit
       - Identifiers
       - Operators: == != > >= < <= + - * / % | =
       - Punctuation: { } [ ] ( ) , : .

  4.2  Lexer
       Status: complete
       - Input: &str
       - Output: Vec<Spanned<Token>>
       - Hand-rolled, no external crates
       - Handles whitespace and -- line comments
       - Handles string escapes and Unicode inside strings
       - Tracks line/column for errors
       - Tests cover exact milestone token stream and representative queries

  4.3  AST definitions
       Status: complete
       - Statement:
           Pipeline(Pipeline)
           CreateCollection { name, schema }
           DropCollection { name }
           CreateIndex { collection, fields }
           DropIndex { collection, fields }
       - Pipeline = Vec<Stage>
       - Stage:
           From { collection, index_hint }
           Where { expr }
           Select { items }
           Drop { fields }
           Order { keys }
           Limit { n }
           Offset { n }
           Group { fields }
           Join { collection, left_field, right_field }
           Insert { docs }
           Update { assignments }
           Delete
       - Expr:
           Field, Lit, BinOp, UnaryOp, In, Exists, Missing,
           StringMatch, Ternary, ArrayLit, DocLit, AggCall
       - Schema AST supports int, float, string, bool, any plus required/unique
       - Document literals preserve field order for deterministic inserts

  4.4  Parser
       Status: complete
       - Input: &[Spanned<Token>]
       - Output: Statement
       - Recursive descent parser
       - Parses top-level DDL statements and pipelines
       - Parses expression precedence for or/and/not/comparison/arithmetic
       - Parses if/then/else ternaries
       - Parses select aliases and simple aggregate forms
       - Parses insert document/batch literals and nested arrays/documents
       - Parses update assignments and delete stages
       - Reports parse errors with line/column
       - Tests cover milestone AST, representative queries, precedence,
         malformed constructs, schema parsing, index DDL, and mutation syntax

  Phase 4 milestone:
    Complete. This query parses without error and matches the expected AST:

      from users | where age > 18 and country == "CA"
                 | order name asc
                 | select name, email
                 | limit 25

  Important boundary:
    Phase 4 parses DDL and mutation syntax, but does not execute it. Creating
    collections, creating indexes, inserting, querying, updating, and deleting
    real data are Phase 5+ runtime work.

PHASE 5 — QUERY ENGINE V1
Status: COMPLETE
----------------------------------------------------------------
Goal: execute the useful Phase 4 AST surface against real data.

Scope delivered:
  End-to-end DDL, reads, mutations, index-aware planning, and persistence are
  implemented. Sort, grouping, aggregates, and inner hash joins were also
  completed as part of the current engine.

Usage story:
  ASL is the database command/query language. In Phase 5 it should be usable
  through the tokenize -> parse -> bind -> plan -> execute pipeline for:
  - schema/data-definition commands:
      create users { id: int required unique, name: string, age: int }
      create index on users.id
  - small/manual inserts:
      from users | insert { id: 1, name: "alice", age: 25 }
      from users | insert [
        { id: 1, name: "alice", age: 25 },
        { id: 2, name: "bob", age: 17 }
      ]
  - normal read queries:
      from users | where age >= 18 | select name, age

  Bulk data loading is not an ASL language feature for v1. Do not add syntax
  like `load users from "users.csv"` in Phase 5. Bulk import belongs in the
  CLI/interface phase as commands that call Database::insert_doc repeatedly.
  CSV and JSONL are the likely first import formats. XLSX import is optional
  later tooling, not core engine work.

  Multi-statement `.asl` files remain an interface concern. The HTTP server
  accepts one ASL statement per POST /query request. There is no
  Database::execute(&str) convenience method yet.

Current query module state:
  src/query/binder.rs, planner.rs, plan.rs, evaluate.rs, and executor.rs are
  implemented and exercised by unit and end-to-end tests.

  5.1  Runtime owner
       Status: complete
       - Introduce Database as the public execution owner
       - Database opens one database file
       - Database owns or coordinates:
           Catalog
           collection access
           IndexManager
           shared BufferPool/DiskManager strategy
       - Hide the current caller-coordinated index maintenance behind Database
         insert/delete APIs
       - Avoid separate Collection and IndexManager views of the same file
         causing flush-boundary surprises

       Implemented:
       - Database::create(path)
       - Database::open(path)
       - has_collection(name)
       - has_index(collection, field)
       - create_collection(name)
       - drop_collection(name), including dropping that collection's indexes
       - create_index(collection, field)
       - drop_index(collection, field)
       - insert_doc(collection, doc), including index maintenance
       - delete_doc(collection, doc_id), including pre-delete document fetch
         and index maintenance
       - get_doc(collection, doc_id)
       - scan_collection(collection)
       - search_index(collection, field, value)
       - range_index(collection, field, low, high)

       Tests cover:
       - create/reopen collection
       - insert and scan
       - index backfill
       - insert updates index
       - delete updates index
       - indexed range fetches documents
       - reopen preserves data and index metadata
       - drop collection removes indexes

  5.2  Binder / validation
       Status: complete
       - Accept Statement from parser
       - Reject nonexistent collections
       - Reject nonexistent indexes for explicit `use index`
       - Validate DDL shape:
           create collection name not already used
           create index target collection exists
           schema field names are unique
       - Validate pipeline order enough for v1:
           pipeline starts with From
           Insert/Update/Delete are terminal
           stages that need a source have one
       - Schema-aware field/type checking can be basic at first because
         catalog schema persistence is not complete yet

       Implemented:
       - bind(db, statement) -> BoundStatement
       - validates collection existence for pipelines and DDL
       - validates explicit index hints
       - validates create/drop single-field indexes against current runtime
         support
       - rejects duplicate schema fields
       - rejects duplicate insert document fields
       - validates terminal Insert/Update/Delete stages
       - rejects aggregate select expressions without a prior group stage
       - keeps composite runtime indexes unsupported until the index layer
         supports them

  5.3  Expression evaluator
       Status: complete
       - eval(expr, document) -> Value
       - truthiness / boolean checks for where
       - Comparisons: == != > >= < <=
       - Boolean ops: and, or, not
       - Arithmetic: + - * / %
       - Unary negation
       - In / not in
       - Exists / missing
       - String contains / starts / ends
       - Ternary if/then/else
       - Int/float coercion where sensible
       - Clear errors for invalid type combinations

       Implemented:
       - eval(expr, doc) -> Value
       - eval_bool(expr, doc), strict bool result for where
       - lit_to_value(lit)
       - doc_literal_to_document(lit), restricted to literal/composite values
         for now
       - field lookup returns Null for missing fields
       - standalone expression evaluation rejects aggregate calls; the group
         executor evaluates them over grouped rows

  5.4  Planner V1
       Status: complete
       - Bound pipeline -> physical plan
       - Physical operators for v1:
           SeqScan
           IndexScan for simple indexed predicates
           Filter
           Projection / Drop
           Limit / Offset
           Insert
           Delete
           CreateCollection
           CreateIndex
           DropCollection
           DropIndex
       - Simple index rule:
           use IndexScan for a single-field indexed equality or a bounded
           `and` range on the same field
           one-sided ranges currently fall back to SeqScan until the BTree
           supports open-ended bounds
           otherwise use SeqScan + Filter
       - No cost model in v1
       - Also plans order, group, aggregate, inner hash join, and update

  5.5  Executor V1
       Status: complete
       - Execute physical plan against Database
       - For read pipelines, return Vec<Document> initially
       - Keep operator boundaries clean enough to move toward streaming later
       - SeqScan reads Collection::scan()
       - IndexScan gets DocIds from IndexManager then fetches docs by DocId
       - Filter applies expression evaluator
       - Projection builds output documents
       - Limit/Offset apply result slicing
       - Pull-based operators materialize Vec<Document> at the result boundary

  5.6  Mutation execution
       Status: complete
       - Insert:
           convert parsed DocLiteral to Document
           call Database::insert_doc
       - Delete:
           identify matching DocIds
           call Database::delete_doc
       - Update uses delete+insert semantics with index maintenance
       - Mutations return QueryOutput::Affected

  5.7  Persistence
       Status: complete
       - DDL and mutations flush as needed for restart tests
       - Restart process, reopen Database, rerun query, same result

  Phase 5 milestone:
    Complete and covered by end-to-end restart tests:

      create users { id: int required unique, name: string, age: int }
      create index on users.id
      from users | insert { id: 1, name: "alice", age: 25 }
      from users | insert { id: 2, name: "bob", age: 17 }
      from users | where age >= 18 | select name, age
        -> [{ name: "alice", age: 25 }]

    Restart. Query again. Same result.

  Phase 5 verified coverage:
    - DDL creates persistent collections and indexes
    - Insert updates indexes
    - Where/select/limit/offset over SeqScan
    - Where/select over IndexScan
    - Delete updates indexes
    - Restart preserves catalog, data, and index metadata

PHASE 7 — v1 RELEASE READINESS
Status: REQUIRED BEFORE v1.0
----------------------------------------------------------------
Goal: publish a narrow, honest, durable v1 rather than expand the language.

v1 product contract:
  A single-process document database with durable files, a schemaless mode,
  ASL queries, secondary indexes, TTL expiration, an embedded Rust API, and a
  local/private-network HTTP interface. It is not yet a transactional,
  multi-writer, or internet-facing database.

  7.1  One storage owner per database
       Status: release blocker
       - Fix the ignored multi-collection corruption test in
         tests/multi_collection.rs
       - Database owns one DiskManager and BufferPool for the whole file
       - Collection, Catalog, HeapFile, and IndexManager borrow or share that
         coordinated storage owner instead of opening independent pools
       - Prevent overlapping allocators from assigning the same page
       - Remove the test ignore and verify data after restart

  7.2  Schema contract
       Status: release blocker
       - Persist declared schema metadata in the catalog
       - Enforce int, float, string, bool, and any on insert/update
       - Enforce required fields
       - Implement unique with a maintained unique index or reject it clearly
       - If persistence cannot ship in v1, reject non-empty schemas instead of
         accepting and silently discarding them
       - Add reopen, malformed-schema, and constraint violation tests

  7.3  Data/index consistency
       Status: release blocker
       - Document the non-transactional write boundary explicitly
       - Add an index consistency checker that compares index entries with
         live heap documents
       - Add online/offline index rebuild commands
       - Make failed index creation clean up allocated pages and metadata
       - Add failure-injection tests between heap, index, catalog, and flush
         steps for insert, update, delete, create index, and drop index
       - Never silently return incomplete indexed results after detected
         inconsistency; fail loudly with repair guidance

  7.4  Panic and corruption hardening
       Status: release blocker
       - Audit panic!, assert!, unwrap(), and expect() in non-test code
       - Convert user input, unsupported index keys, malformed pages, pinned
         frame exhaustion, and invalid on-disk state into typed errors
       - Preserve assertions only for invariants proven by private callers
       - Fuzz lexer, parser, document decoder, catalog decoder, BTree node
         decoder, and HTTP request parsing
       - Ensure one malformed query or file cannot terminate the server

  7.5  Stable execution API
       Status: required
       - Add Database::execute(&str) -> Result<QueryOutput>
       - Centralize tokenize, parse, bind, DDL, plan, and execute behavior
       - Make HTTP, future REPL, tests, and embedded callers use the same path
       - Define which Rust modules/types are stable public API

  7.6  File-format contract
       Status: release blocker
       - Add file magic, format version, and compatibility checks
       - Reject unsupported newer formats without modifying the file
       - Define v1.x compatibility and migration policy
       - Provide validate, backup, restore, and export paths before migrations
       - Test truncated, corrupted, older, and unknown-version files

  7.7  Resource limits
       Status: required
       - Configurable buffer-pool capacity
       - Maximum HTTP body, result rows/bytes, join build size, group count,
         collect size, and in-memory sort size
       - Query timeout or cooperative cancellation
       - Clear limit errors instead of process-wide OOM or unbounded work
       - TTL sweeps operate in bounded batches

  7.8  Lifecycle and operations
       Status: required
       - Graceful shutdown stops accepting requests, joins the TTL worker,
         completes active work, and flushes dirty pages
       - Refuse unsafe public bind addresses unless explicitly requested, or
         print a prominent warning about missing authentication and TLS
       - Add asdb info, validate, backup, restore, rebuild-index, and compact
         command foundations
       - Use stable exit codes and machine-readable diagnostics

  7.9  Verification and packaging
       Status: required
       - CI on Linux and Windows: format, lint, build, unit, integration, and
         doc tests
       - All normal tests pass; no ignored known-correctness failures
       - Run large stress tests and fuzz smoke tests in scheduled CI
       - Benchmark a release build on a documented machine and dataset
       - README, architecture guide, ASL reference, HTTP examples, backup and
         recovery guide, limitations, license, changelog, and release notes
       - Reproducible release binaries and checksums

  v1.0 release gates:
    [ ] Multi-collection persistence test passes without #[ignore]
    [ ] Schema declarations are enforced or explicitly rejected
    [ ] Index validation and rebuild succeed after injected partial failures
    [ ] No user-controlled input reaches an unhandled panic
    [ ] File magic/version and compatibility tests pass
    [ ] Graceful shutdown and bounded-resource tests pass
    [ ] Linux and Windows CI are green
    [ ] Release benchmarks and operational documentation are published

PHASE 8 — DURABILITY, RECOVERY, AND TRANSACTIONS
Status: POST-v1 PRIORITY
----------------------------------------------------------------
Goal: make acknowledged writes recoverable and atomic across engine layers.

  8.1  Write-ahead log
       - WAL records with checksums, sequence numbers, and format version
       - Write and fsync log records before dirty data pages
       - Startup analysis and redo of committed operations
       - Idempotent replay and torn-tail detection
       - Checkpoints and safe WAL truncation

  8.2  Atomic statements
       - Begin/commit/abort around each mutation statement
       - Undo or compensation for incomplete heap, BTree, and catalog changes
       - Atomic multi-document insert/update/delete within one statement
       - Crash tests at every persistence boundary

  8.3  Explicit transactions
       - ASL/API begin, commit, and rollback
       - Read-your-writes and repeatable error semantics
       - Savepoints as a later extension
       - Define durability modes: synchronous, balanced, and unsafe-fast

  8.4  Backup and recovery
       - Consistent online snapshots coordinated with WAL/checkpoints
       - Point-in-time recovery from snapshot plus archived WAL
       - Backup verification and restore drills in CI

PHASE 9 — STORAGE LIFECYCLE AND ADVANCED INDEXES
Status: POST-v1
----------------------------------------------------------------
Goal: control file growth and broaden efficient access paths.

  9.1  Vacuum and compaction
       - Reclaim tombstoned heap slots and empty pages
       - Compact page chains and return free pages to the allocator
       - Online incremental vacuum with bounded work
       - Report reclaimable and reclaimed bytes

  9.2  Index improvements
       - Open-ended range scans for one-sided predicates
       - Composite indexes with lexicographic key encoding
       - Unique, sparse, and partial indexes
       - Covering/index-only scans
       - Background index build and rebuild
       - Prefix scans where string encoding permits them

  9.3  Large values and richer data
       - Overflow pages for documents and index keys larger than one page
       - Optional binary and timestamp value types
       - Defined numeric coercion, NaN, infinity, and collation behavior
       - Per-document size limits with actionable errors

  9.4  Format evolution
       - Forward migrations with preflight validation and rollback plan
       - Feature flags in the file header
       - Offline and eventually online migration tooling

PHASE 10 — COST-BASED QUERY ENGINE
Status: POST-v1
----------------------------------------------------------------
Goal: turn the clean physical-operator model into a measured optimizer.

  10.1 Statistics
       - Row counts, null fractions, distinct estimates, min/max, and sampled
         histograms per collection/index
       - Analyze command and incremental statistics maintenance
       - Persist statistics with freshness metadata

  10.2 Cost model
       - Estimate sequential scan, index scan, filter, sort, group, and join
         cardinalities and costs
       - Choose indexes by selectivity rather than first-match rules
       - Combine useful predicates and choose join order/strategy
       - EXPLAIN and EXPLAIN ANALYZE with estimates versus actuals

  10.3 Execution at scale
       - External merge sort with spill files
       - Spillable hash aggregation and hash join
       - Top-N sort for order + limit
       - Projection/filter pushdown and limit pushdown
       - Vectorized/batched operators where benchmarks justify them
       - Query memory accounting and cancellation cleanup

  10.4 Language depth
       - Left/right/full outer joins
       - Subqueries and nested pipelines
       - Window functions
       - Additional statistical aggregates and approximate distinct counts
       - Explainable, backwards-compatible ASL grammar evolution

----------------------------------------------------------------
PHASE 11 — CONCURRENCY AND SERVER HARDENING
Status: POST-v1
----------------------------------------------------------------
Goal: move from serialized local service to safe multi-client operation.

  11.1 Concurrency control
       - Multiple concurrent readers
       - Page/record or MVCC-based write coordination selected by prototype
         and benchmark evidence
       - Deadlock prevention/detection or timestamp ordering
       - Isolation levels with conformance tests

  11.2 Production server
       - Bounded worker pool or async I/O instead of a thread per connection
       - Keep-alive, chunked bodies, backpressure, timeouts, and cancellation
       - TLS and optional mutual TLS
       - Authentication, database roles, and collection-level authorization
       - Rate limits, request IDs, structured audit logging, and safe defaults

  11.3 Observability
       - Structured logs with stable event fields
       - Metrics for latency, throughput, cache hit rate, evictions, flushes,
         WAL/checkpoint lag, query memory, TTL work, and error classes
       - Readiness separate from liveness
       - Slow-query log and operator-level execution profiles

PHASE 12 — DEVELOPER EXPERIENCE AND ECOSYSTEM
Status: POST-v1
----------------------------------------------------------------
Goal: make asdb pleasant to adopt, inspect, automate, and extend.

  12.1 First-party tools
       - REPL with multi-line editing, history, completion, and explain views
       - Multi-statement file execution with clear transaction behavior
       - Streaming CSV and JSONL import/export with row-level diagnostics
       - Shell-friendly JSON output and human-friendly tables

  12.2 Client ecosystem
       - Versioned HTTP API and capability negotiation
       - Rust client plus generated or hand-written Java, Python, and
         TypeScript clients
       - Connection pooling, retries limited to safe/idempotent operations,
         and typed errors

  12.3 Extensions
       - Stable function/aggregate extension interface
       - Optional user-defined functions in a sandboxed runtime such as WASM
       - Pluggable tokenizers for eventual full-text search
       - Extension versioning and resource limits

PHASE 13 — SEARCH, ANALYTICS, AND DISTRIBUTION
Status: LONG-TERM
----------------------------------------------------------------
Goal: pursue differentiating capabilities only after the single-node core is
durable, observable, and benchmarked.

  13.1 Search
       - Inverted full-text indexes, tokenization, ranking, and highlighting
       - Geospatial point indexes and radius/bounding-box queries
       - Optional vector type, approximate nearest-neighbor index, metadata
         filtering, and hybrid lexical/vector ranking

  13.2 Analytics
       - Columnar temporary batches for analytical operators
       - Parallel scans, joins, and aggregation on large local datasets
       - Materialized views with refresh policies
       - Parquet import/export and predicate pushdown

  13.3 Replication
       - Physical or logical replication selected after WAL semantics stabilize
       - Leader/follower failover with fencing and split-brain prevention
       - Read replicas and lag visibility
       - Online backup from replicas

  13.4 Distribution
       - Explicit partitioning/sharding keys
       - Routing, rebalancing, and distributed query planning
       - Consensus-backed metadata and membership
       - Distributed transactions only if demonstrated use cases justify them

----------------------------------------------------------------
BENCHMARK PROGRAM
----------------------------------------------------------------
Benchmarks are release evidence, not one-off marketing numbers. Preserve raw
results, configuration, commit, compiler, OS, hardware, and dataset generator.

  B1  Insert/update/delete throughput
      - 1M, 5M, and 10M documents
      - Sequential and random indexed values
      - With zero, one, and several indexes
      - Report logical throughput, physical bytes, and fsync policy

  B2  Point and range reads
      - Indexed versus sequential lookup
      - p50, p95, p99, and maximum latency
      - Cold cache, warm cache, and mixed read/write workloads
      - Range selectivity from 0.01% through 100%

  B3  Query operators
      - Sort, Top-N, group cardinality, aggregate, and join build/probe sizes
      - Memory consumption and spill behavior
      - Estimate accuracy after cost-based planning exists

  B4  Buffer pool and storage
      - 10%, 25%, 50%, and 100% of working set
      - Hit rate, eviction rate, dirty flushes, read/write amplification
      - Fragmentation and vacuum effectiveness over churn workloads

  B5  Durability and concurrency
      - WAL/checkpoint overhead by durability mode
      - Recovery time by database/WAL size
      - Scaling across readers and writers with tail latency
      - Long-running soak tests with crash/restart injection

  B6  Comparative discipline
      - Compare only equivalent durability and indexing configurations
      - Publish workloads and scripts
      - Track regressions with budgets in CI; never optimize away correctness

----------------------------------------------------------------
DELIBERATE NON-GOALS
----------------------------------------------------------------
- Shipping every post-v1 feature before the first stable release
- SQL compatibility at the cost of a coherent ASL design
- A custom binary wire protocol before HTTP profiling proves it necessary
- Distributed execution before WAL, recovery, transactions, and replication
- Lock-free or NUMA-specific optimization before representative benchmarks
- Silent recovery that hides detected corruption or data loss
- Depending on crates for core storage/query algorithms merely to add features

----------------------------------------------------------------
LONG-HORIZON STRETCH GOALS
----------------------------------------------------------------
- Adaptive radix tree or LSM index experiments beside the BTree
- Learned cost/cardinality models guarded by deterministic fallbacks
- Incremental materialized views and change-data capture streams
- Temporal collections and time-travel queries backed by MVCC history
- Tiered hot/cold storage and object-store snapshots
- Compression for pages, documents, WAL, and network results
- Content-addressed backup deduplication
- NUMA-aware buffer pools and parallel vectorized execution
- Embedded WASM functions with deterministic resource metering
- Hybrid full-text, vector, structured, and geospatial retrieval

----------------------------------------------------------------
SUGGESTED CRATES
----------------------------------------------------------------
- Keep storage, WAL, BTree, parser, binder, planner, and executor algorithms
  hand-rolled so their invariants remain visible and educational
- Use mature crates at system boundaries where reimplementation creates risk:
    clap             CLI parsing and stable help output
    rustyline        REPL editing/history
    serde/serde_json optional interoperability at the JSON boundary
    rustls           TLS instead of custom cryptography
    tracing          structured logs and spans
    proptest         property tests for codecs and data structures
    cargo-fuzz       fuzz targets for untrusted inputs
- Every dependency needs a concrete benefit, license review, maintenance
  check, and measurable compile/runtime impact
